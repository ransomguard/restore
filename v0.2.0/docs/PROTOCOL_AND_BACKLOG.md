# 현재 프로토콜과 자동 대응 전 남은 작업

이 문서는 이번 통합 소스의 구현 경계를 기록한다. 기준은 별도 `knel` 저장소의 `Shared/Common.h`, `Anti_Ransom_Driver`, `Anti_Ransom_FsFilter`와 `store/ransomguard`다. Windows 실행 검증 완료 문서가 아니다.

**선택한 네트워크 목표는 의심 프로세스 단위 격리**다. 별도 정상 엔진은 JEV·중앙 대시보드와 통신하고, 의심 프로세스에는 JEV 예외를 열어 주지 않는다. PC 전체 격리는 이번 선택 범위가 아니다. 현재 `network_policy.py`는 이 요구를 검증하고 계획을 출력할 뿐 WFP/방화벽 필터를 설치하지 않는다. `plan_only=true`, `network_changed=false`는 실제 격리가 적용되지 않았다는 뜻이다.

## 1. 정확한 현재 ABI

장치 경로는 `\\.\RansomGuard`, Magic은 `0x41525747`, Version은 `0x00010000`이다. IOCTL은 `METHOD_BUFFERED`다. 아래 크기는 바이트이며 이벤트 크기에는 32바이트 공통 헤더가 포함된다. 문자열은 UTF-16LE이고 길이 필드는 종료 NUL을 제외한 **바이트 수**다.

| 항목 | 크기 | 핵심 필드/용도 |
| --- | ---: | --- |
| `ARW_EVENT_HEADER` | 32 | Magic, Version, EventType, PayloadSize, TimeStamp, SequenceNumber |
| `ARW_PROCESS_EVENT` | 1616 | PID·부모 PID·생성 요청자 PID, 생성 시간, 규칙 ID, 이미지 경로, 명령행 |
| `ARW_FILE_EVENT` | 2232 | PID, write/rename 구분, 파일 경로, 새 확장자, 관측 플래그 |
| `ARW_EVENT_ANY` / GET_EVENT 최소 출력 버퍼 | 2232 | 수신 버퍼는 항상 최대 크기 확보; 실제 반환 바이트와 헤더를 검증 |
| `ARW_REGISTER_REQUEST` | 8 | Magic, Version. 호출자 PID를 사용자 입력으로 받지 않음 |
| `ARW_TERMINATE_REQUEST` | 24 | PID, Reason, 0이 아닌 ExpectedCreateTime |
| `ARW_TERMINATE_RESPONSE` | 16 | 대상 PID, 실제 명령 결과 NTSTATUS |
| `ARW_POLICY_REQUEST` | 20 | fast path 모드, 프로세스 감시/자기 보호 정책 |
| `ARW_STATUS_RESPONSE` | 72 | 현재 정책·엔진 PID·큐 깊이·생성/유실/전달/폐기/차단/종료 카운터 |

현재 IOCTL 값은 register `0x8123A000`, unregister `0x8123A004`, terminate `0x8123A008`, update policy `0x8123A00C`, status `0x81236010`, event `0x81236014`다. 헤더에 선언된 `IOCTL_RG_REPORT_VSS_ATTEMPT`는 제어 드라이버 디스패치 구현이 없으므로 동작하는 VSS 보호 채널로 간주하지 않는다.

프로세스 생성 시간 오프셋은 48, 이미지 경로는 72, 명령행은 592다. 파일 경로는 56, 새 확장자는 2104다. Python 디코더는 타입별 크기, 실제 반환 길이, Magic/Version, 문자열 길이 및 UTF-16을 검사한다. `PayloadSize`는 본문만의 길이가 아니라 해당 이벤트 전체 길이다.

엔진은 등록한 장치 파일 객체와 최초 open 프로세스에 묶인다. 같은 등록 핸들로 이벤트와 명령을 처리해야 한다. 다른 프로세스의 복제 핸들 및 별도 open 핸들은 등록 권한을 이어받지 않는다. `GET_EVENT`는 이벤트가 없으면 대기한다. `DeviceIoControl` 성공만으로 대상 종료를 판단하지 않으며, `ResultStatus` 확인 뒤 프로세스 종료를 따로 확인한다.

## 2. 현재 상관관계와 관측의 한계

프로세스 이벤트에는 생성 시간이 있지만 **파일 이벤트에는 PID만 있고 생성 시간이 없다.** 프로세스 생성 이벤트로 유지한 PID→생성 시간 캐시는 상관분석을 돕지만 파괴적 대응의 충분한 근거가 아니다. 엔진 시작 전 생성된 프로세스, 누락된 수명 이벤트, PID 재사용, 동시 생산자의 순서 변경을 처리해야 한다. 현재 `ProcessRegistry`는 sequence 이상 시 캐시를 비우지만, sequence가 연속이라는 사실도 관측 완전성을 보장하지 않는다.

커널 이벤트 큐는 최대 1024건이고 넘치면 오래된 항목을 버린다. 등록 해제/언로드는 남은 항목을 폐기한다. 생성 순서와 전달 순서가 항상 같다는 보장이 없고, sequence를 받기 전에 누락된 관측은 번호 공백만으로 찾을 수 없다. 상태 카운터·발신 측 제한·시작 시점도 함께 기록해야 한다. `SequenceNumber`는 영속적인 사건 ID나 프로세스 ID가 아니다.

현재 미니필터는 일반 비 paging IRP write와 일부 rename 시도를 관측한다. fast I/O, paging/memory-mapped 경로, create/truncate/delete 등 전체 변경 경로를 완전히 다루지 않는다. write/rename 이벤트는 **pre-operation 관측**이며 I/O 성공 여부나 최종 바이트를 증명하지 않는다. 높은 엔트로피 플래그는 탐지 신호이며 악성 확정값이 아니다. rename에는 이전 경로와 점 없는 새 확장자가 들어가며, 새 전체 경로·안정적인 파일 ID·최종 I/O 결과가 없다. 경로 잘림/미확보와 확장자 미확보 플래그도 별도로 처리해야 한다.

fast path의 BLOCK 동작은 프로세스 생성 콜백에서 `CreationStatus=STATUS_ACCESS_DENIED`로 **생성하려던 프로세스를 거부**한다. 이미 실행 중인 부모·생성 요청자 프로세스를 kill한 결과가 아니다. `process_creation_blocked` 로그를 “랜섬웨어 본체 종료 확인”으로 바꾸어 표시하면 안 된다.

새 설치의 기본 fast path는 `AUDIT(1)`이다. 이전 레지스트리 정책이 있으면 그 값이 우선하고, Python `observe`는 정책을 변경하지 않는다. 커널에는 명시적으로 선택 가능한 BLOCK 모드와 수동 종료 IOCTL이 남아 있다. 실제 로드된 정책은 상태 조회로 확인한다.

## 3. 실시간 자동 대응을 연결하기 전의 필수 작업

| 영역 | 현재 상태 | 자동 대응 전 완료 조건 |
| --- | --- | --- |
| 프로세스·파일 식별 | 프로세스 generation은 있으나 파일 이벤트에는 없음 | 파일 이벤트에 신뢰할 수 있는 프로세스 instance 식별을 넣는 버전 변경/호환 정책. 볼륨·파일 ID, rename 전후 경로, 작업 결과를 포함한 연계. 시작 당시 실행 중인 프로세스와 유실 처리 |
| 파일 변경 관측 | 제한된 write/rename 시도와 전역 예산 제한 | 대응 범위의 create/write/truncate/rename/delete, fast/paging/mapped I/O 경로를 검토하고 VM에서 누락·성공/실패·중복을 검증. 관측 밖 경로는 명시적으로 기록 |
| 실제 파일 보호 | 현재 미니필터는 파일 I/O를 차단하지 않음. 상태 머신의 `file_hold`는 모의 효과 | 의심 프로세스/대상 파일에 대한 실제 쓰기 억제, 신규 핸들·기존 핸들·매핑 경로 처리, 대기 취소/시간 제한/교착 방지. 적용 완료 확인 후 JEV 대기 또는 복구로 진행 |
| 실제 프로세스 네트워크 격리 | 정책 계획만 있고 필터 없음 | 검증된 WFP 백엔드, 규칙 우선순위·트랜잭션·식별자 관리, IPv4/IPv6 및 이미 열린 흐름까지 차단 검증. 격리 적용과 해제 결과를 OS에서 확인 |
| 프로세스/엔진 신원 | 프로세스별 격리 범위와 정상 엔진의 통신 목적지를 계획으로 표현 | PID 재사용을 막는 실제 프로세스 instance 연결, 자식/대리 통신 범위, IPv4/IPv6의 기존 흐름 차단. 정상 엔진과 의심 프로세스를 구분하며 모든 프로세스에 열리는 IP 예외로 대체하지 않음 |
| 사건 상태와 재시작 | 로그 outbox는 영속적; 사건/hold 상태는 메모리의 시뮬레이터 | incident·프로세스 instance·상태 버전·JEV request·규칙 소유권/hold를 영속 저장. 시작 시 실제 OS 상태와 대조하고 미완료 격리를 복구. 충돌/재부팅 후 검증 전 일괄 해제하지 않음 |
| 종료 완료와 후손 | 수동 종료 명령은 generation 확인. 모의 대응은 실제 종료를 수행하지 않음 | 원본 프로세스 핸들의 종료 확인, 자식/후손 및 새 생성 경쟁 처리. 부모 PID 하나만으로 트리 신뢰하지 않음. 실패/시간 초과면 미확인 상태 유지 |
| 복구 대상과 버전 | 명시적 manifest와 사건 이전 VSS snapshot을 사용하는 복구 모듈 | 탐지 증거에서 신뢰할 manifest를 만드는 단계, 정확한 볼륨/원본·이동 경로/파일 버전 연계, 복구 후 파일별 결과 검증. 동시 쓰기·디렉터리 교체를 억제하고 부분 실패 처리 |
| JEV·대시보드 연동 | 파싱/전송 계층 및 로컬 기록은 존재 | 실제 endpoint, 인증, 요청/응답/ACK 스키마, 점수 의미와 검증된 임계값, 시간 제한/재시도/중복 제거 계약. endpoint에서 통합 검증 |

네트워크 백엔드는 신규 연결만 막는 것을 기존 세션 차단 완료로 보고하면 안 된다. 이미 연결된 TCP, UDP/QUIC, IPv6, VM의 실제 어댑터와 LAN/SMB 경로까지 선택한 프로세스 격리 범위에서 검증한다. 정상 엔진의 DNS/JEV/대시보드 통신 유지와 의심 프로세스의 DNS 차단을 각각 확인한다. 주소 변경을 처리하되 의심 프로세스에 제어 서버 IP를 예외로 열어 주지 않는다. 최초 DNS 조회 결과는 영구 IP 목록이 아니다. 설치된 전체 방화벽 규칙을 초기화하는 대신 사건이 소유한 필터와 예외만 관리한다.

사건 A 하나의 정상 판정 또는 종료 확인으로 사건 B의 격리까지 풀리지 않도록 process-network/file hold 소유권을 유지해야 한다. JEV timeout, 애매한 점수, 오래된 응답, 복구 실패는 “정상”이나 “해제 가능”을 뜻하지 않는다. 현재 시뮬레이터의 `incident_id + request_id + state_version` 검사와 참조 유지 규칙을 실시간 실행기·영속 저장으로 옮겨 검증해야 한다.

복구 모듈은 각 파일의 staging 내용 해시 확인과 교체를 제공하지만, manifest 전체가 하나의 원자적 작업은 아니다. 내용 해시 일치는 복사 무결성 확인이며 선택한 과거 버전이 업무상 올바른 버전이라는 증거와는 별개다. ACL/ADS/EFS/reparse 복구는 현재 계약 밖이다. snapshot 생성 주기는 사용자 결정으로 1시간(3600초), 정기 생성만 허용하는 것으로 확정했다. 탐지·JEV·복구·서비스 시작에 따른 추가 생성은 없다. 주기 생성은 v0.6.1의 `snapshots.py`와 예약 작업으로 구현했다. 보존 정책 구현, 건강한 기준본 확인, snapshot 이후 정상 변경의 처리, 새 악성 파일과 rename 잔재 처리는 남아 있다. 적절한 기존 사본이 없으면 복구 불가를 기록한다.

## 4. 중앙 로그의 완료 조건

대시보드는 `requested`, `applied`, `failed`, `confirmed`를 구분해야 한다. 특히 격리 요청과 실제 적용, 종료 명령 수락과 종료 확인, 복구 복사 종료와 검증 완료를 각각 별도 사건으로 표현한다. `simulation`/`observation` 모드를 표시해 모의 `quarantine_applied`를 실제 WFP 적용으로 집계하지 않는다.

최소 계약에는 고유 event ID, incident ID, agent/host ID, 프로세스 PID+생성 시간, 상태 버전, 발생/수신 시각, 결과·실패 원인, 재전송 시 중복 제거 키가 필요하다. 로컬 outbox 저장 이후 중앙 ACK를 받기 전에는 전달 완료로 지우지 않는다. 중앙 서버의 ACK 형식과 중복 처리, 단절 후 재전송을 실제 백엔드에서 확인한 뒤 완료로 판단한다.

해제 시점에 대한 현재 모의 구현은 **정상 판정 또는 위협의 종료·필요 복구 검증이 확인되고, 해당 사건의 hold를 제거해도 다른 사건의 hold가 남지 않는 시점**이다. kill 명령을 보냈다는 사실이나 타이머 만료만으로 해당 프로세스의 통신 규칙을 해제하는 규칙은 구현하지 않는다. 이 조건은 현재 모의 상태 전이에 표현되어 있으며 실시간 OS 적용은 위의 미완료 백엔드와 검증이 필요하다.

## 5. v0.6.1의 고엔트로피 연결

`triage.TriageIntake.ingest`가 `ARW_FILE_FLAG_HIGH_ENTROPY` 쓰기 신호를 Track B 후보로 분류한다. CLI `observe`는 원본 이벤트와 후보/신원 보류 레코드를 outbox에 저장한다. 반복 후보 억제와 write/rename 집계가 있으나 후보는 자동 격리·JEV 요청·악성 판정이 아니다. `docs/TRIAGE_KO.md`의 제한을 따른다. 드라이버 유실 상태는 현재 관측 시작/종료 시 조회하므로, 실행 중 counter-only 유실의 즉각적인 신원 무효화는 후속 구현이다.
